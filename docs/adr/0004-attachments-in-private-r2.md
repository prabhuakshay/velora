# Attachments live in a private R2 bucket and are cleaned up with their records

Attachments are stored in a private Cloudflare R2 bucket and opened through short-lived presigned URLs, because receipts are sensitive and the prod container's filesystem is read-only. Uploads go through Django, not straight from the browser to R2, so every file is checked before it is stored and nothing is uploaded without a Transaction to own it. Files are written to R2 inside the database transaction; on a handled error the files already written are always removed, so cleanup is only best-effort when the process is killed: a crash or force-kill between writing to R2 and committing can leave a stray object. We accept this, since the bucket is private and a stray object only wastes storage. Deleting an Attachment or its Transaction, by any route, queues a background job in the same database transaction (ADR 0005), and that job deletes the R2 object after the commit and retries on failure. A delete never fails because R2 is down, and a rolled-back delete leaves no job behind. An object R2 reports as already gone counts as deleted. A job that runs out of retries leaves an Untracked object: we accept this, as with a stray upload. R2 has no per-object ACLs, so privacy rests on the bucket itself being private (no public access and no r2.dev URL): objects are only reachable through presigned URLs.
